Appium Mobile E2E: Android + iOS, one codebase

  • Appium 3
  • WebdriverIO 10
  • TypeScript
  • Android emulator
  • Allure
  • Appium MCP
  • Claude Code

A cross-platform suite against Sauce Labs' My Demo App (React Native): one set of Screen Objects drives Android and iOS through shared accessibility ids. State is set with deep links instead of replaying the UI, and every test starts from a clean app. It goes past the happy path: gestures, NATIVE ↔ WEBVIEW switching, mocked GPS, background and screen-lock interruptions, and SauceDemo in the emulator's real Chrome (touch, on-screen keyboard, rotation).

App bugs found and documented along the way: Add To Cart on deep-linked product pages adds an item with no price, payment errors vanish on submit, and the app crashes whenever Android recreates its activity.

64 tests in 18 spec files · native app and mobile web on an Android API 34 emulator · smoke gate on every push, CI in about 4 min · iOS CI on the roadmap

02 · Case study

Case study: AI in the QA flow

Not a prompt collection: a pipeline I use every day on two betting platforms, with a human reviewing at the end.

Details anonymized due to NDA.

  1. Feature description
  2. Test cases and acceptance criteriaClaude Code skill
  3. Playwright specvia MCP
  4. Run in CI
  5. Triage
  6. Jira-ready bug report

Context

I own quality end to end for two betting brands, across web, mobile web and native app: sportsbook, live betting and casino flows.

Problem

Test cases were written by hand for every new feature, on web, mobile web and native app.

Approach

Claude Code skills turn a feature description into test cases and acceptance criteria. Agents map the pages through Playwright MCP and draft the Playwright tests, CI runs them, and failures are triaged into Jira-ready bug reports. Generated tests are drafts: a human reviews everything before merge, and anything the agent can't confirm is marked test.fixme instead of guessed.

Result

2h → 5min to write the test cases for a feature.
